## 修复：切换主题崩溃（TDZ）+ 双主题系统根因
- **报错**：`Uncaught (in promise) ReferenceError: Cannot access 'isDark' before initialization`（app.ts:54 applyTheme → initialize:134）
- **根因**：`applyTheme` 在第 54 行 `if (isDark)` 提前引用了 `isDark`，但 `const isDark` 声明在第 57 行（暂时性死区 TDZ）→ 函数第 54 行直接抛错，`applyTheme` 中断 → `useAppStore`(System A) 的布局 CSS 变量（--bg-color/--text-color/--layout-*-background 等）从未注入 → 切换主题"没生效"
- **修复**：把 `const isDark = effectiveTheme === 'dark';` 上移到 `toggleHtmlClass(DARK_CLASS)` 之前（app.ts 现第 53 行）
- **架构坑（重要）**：项目存在**两套独立主题系统**且都往 `document.documentElement` 写 `.dark` 类
  - System A `src/stores/app.ts` `useAppStore`：`theme`(light/dark/system)，UI 开关在 Login.vue:306 + SettingsDrawer.vue:355，注入布局用 CSS 变量（--layout-*/--bg-color 等）到 root 内联样式
  - System B `src/stores/theme/index.ts` `useThemeStore`：App.vue 始终挂载，`themeScheme`(light/dark/auto)，控 `.dark` 类 + `--primary-color`(rgb 三元组) + `n-config-provider` Naive 主题
  - 两者状态互不同步：切 A 的 theme 不会动 B 的 themeScheme，反之亦然。当前 login/设置抽屉走 A，主框架(antd/naive)走 B，属于历史包袱，未统一

## 排查：cc-config 切换环境配置列表不变
- **结论：前端链路自洽，问题在后端 `envType` 过滤**
- 链路：`LayoutHeader.vue` 的 `EnvSelector.vue` → `envStore.setCurrentEnv` → `center.vue` `watch([selectedComponents, currentEnv])`（line 315） → `fetchEnvironmentsData()` → `getConfigEnvironments({configComponentId, envType:Number(currentEnv)})`（configEnvironment.ts 发 `envType`；`ConfigEnvironmentParams` 含 `envType`） → 设 `activeTabKey=environments[0].id` → `getConfigItems({configEnvironmentId,...})`（`ConfigItemParams` 含 `configEnvironmentId`，request.ts 不吞参数）
- 已逐项验证前端无缺陷：store 响应式正常、`currentEnv` computed 触发 watch、请求层（configRequest）不篡改 query、两个接口类型均带 envType/configEnvironmentId
- **根因推断**：`GET /api/v1/configEnvironments` 未按 `envType` 过滤（或 envType 取值契约不一致：前端发 1/2/3，后端若期望 0/1/2 或 'dev'/'test'/'prod' 则过滤失效）→ 返回的 environments 不变 → activeTabKey 不变 → `getConfigItems` 拿到同一 configEnvironmentId → 列表不变
- **待用户确认**：网络面板核对 `envType` 是否发出 + 两个 envType 是否返回不同 environments/configItems
- **【用户纠正1】访问密钥列表不区分环境是 BY DESIGN，不是缺陷**：`access-security.vue` 的 `ConfigAccessKeysParams` 无 `envType`、组件不 watch 环境 —— 这是设计如此（密钥本就不按环境隔离），**不是前端 bug**。我之前把它标成"缺陷"是误判，已收回。
- **【用户纠正2】用户实测"切环境根本没调接口"**：这与上文"前端自洽"结论直接冲突。我重读 `center.vue`/`useConfigData.ts`/`stores/config.ts` 三遍，`watch([selectedComponents, currentEnv])`→`fetchEnvironmentsData()`→`getConfigEnvironments`+`getConfigItems` 在响应式上完全正确，切 `envStore.currentEnv` 必触发请求。所以"没调接口"只可能是：① 用户实际打开的页面 run 的不是 `center.vue`（动态路由 `route.component` 来自后端菜单，静态无法断定）；② `currentEnv` 没真变。光静态读已到头。
- **动作**：在 `center.vue`（watch 回调 + fetchEnvironmentsData 入口）和 `useConfigData.fetchEnvironments` 三处加了 `[DEBUG-ENV]` console.log 临时 trace（build 2.34s 通过）。等用户本地刷新 + 切环境，看 console 是否出现 `watch fired` / `fetchEnvironments -> API` 来定案。trace 确认后需删除。
- **教训**：用户已两次纠正（误判缺陷 + 误信"后端过滤"），排查此类"切环境列表不变"问题不要只靠静态推导，要打 trace 实跑取证；且"没调接口"是客观现象，应优先怀疑"挂载的组件/watcher 是否真的是这段"，而非默认前端链正确就甩锅后端。
- **清理**：`[DEBUG-ENV]` 三处 trace 已删除（center.vue watch + fetchEnvironmentsData 入口 + useConfigData.fetchEnvironments）；以及顺手清掉 `groupView.vue:161` 冗余 `@ts-expect-error`（vue-tsc 已全绿）。
